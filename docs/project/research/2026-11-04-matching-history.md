# Matching history: what has improved, and what issue #260 still exposes

Research baseline: upstream commit [`3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4`](https://github.com/jbms/beancount-import/commit/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4), inspected on 2026-11-04 UTC. This is a history and behavior investigation, not an implementation proposal. Sources are the actual Git diffs, committed tests, and upstream GitHub issue/PR bodies and reviews. No private ledger was read or benchmarked.

## Main finding

There are three different combinatorial operations in this matcher. Improvements to one do not necessarily constrain the others:

1. **Aggregate posting generation:** enumerate subsets of postings within one transaction, grouped by identical account and currency. Those become synthetic postings that let a single payment match several line items.
2. **Pairwise merge generation:** enumerate compatible posting correspondences between two transactions, combine positive and negative groups into balanced match sets, filter dominated sets, and combine results across currencies.
3. **Transaction search:** recursively merge another transaction into each surviving merged state. The state identifier deduplicates paths to the same used-transaction set and posting set; it does not collapse different subsets of transaction identities.

All three are visible in the current [`matching.py`](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching.py#L889). The first has a candidate-count heuristic and recent early termination; the second and third still have no search budget. Issue [#260](https://github.com/jbms/beancount-import/issues/260) describes the third operation's subset explosion for similar transactions, not merely excessive enumeration of item subsets inside one invoice.

## 2016: the broad semantics and exhaustive graph search already existed

Commit [`3fa3951236927c2eff2b95b42a64dcad3b12c77a`](https://github.com/jbms/beancount-import/commit/3fa3951236927c2eff2b95b42a64dcad3b12c77a) introduced the web interface, `matching.py`, matching tests, caller, and UI together. Its module documentation explicitly describes repeated merging: find possible partners, enumerate valid balanced merges, then repeat for every resulting merged transaction. This was designed for more than choosing one duplicate from a list.

The original implementation already had:

- Account compatibility through exact accounts or unknown accounts, posting weights at cost/price, cleared-posting protections, metadata compatibility, and balanced correspondence sets. Two cleared postings cannot merge. One side of a posting correspondence must be a singleton; arbitrary many-to-many aggregation is not supported.
- Unknown-posting removal, subject to restrictions; opposite unknown postings can cancel when a regular match was unavailable. The transaction-level opposite-known-posting heuristic rejects merges that would contain canceling known-account postings.
- Aggregates of 2–4 eligible same-account, same-currency, same-sign postings, plus the entire same-sign account/currency group when larger than four. Cleared, costed, priced, or missing-unit postings were excluded from aggregation.
- A depth-first `get_extended_transactions`, a `previously_seen_states` set, and a state identifier containing both the set of used transaction identities and the set of posting identifiers. Results were materialized, sorted, and normalized only after traversal.
- The current three-part ranking: descending cleared-posting matches, then descending uncleared-posting matches, then ascending unknown-posting removals. There was no date-distance or description-similarity score in that rank.

These are in the [original matcher](https://github.com/jbms/beancount-import/blob/3fa3951236927c2eff2b95b42a64dcad3b12c77a/beancount_import/matching.py), including its [rank function](https://github.com/jbms/beancount-import/blob/3fa3951236927c2eff2b95b42a64dcad3b12c77a/beancount_import/matching.py#L374) and [DFS](https://github.com/jbms/beancount-import/blob/3fa3951236927c2eff2b95b42a64dcad3b12c77a/beancount_import/matching.py#L1400).

The useful multi-transaction behavior has committed evidence: `test_match_many_merged` is an Amazon order with many line items and four actual credit-card transactions corresponding to six invoice payment lines. The golden test enumerates many valid combinations, not a single preferred pair. Other tests preserve partial matches, grouped payments, split unknown accounts, metadata conflicts, and unknown removals. See the [original tests](https://github.com/jbms/beancount-import/blob/3fa3951236927c2eff2b95b42a64dcad3b12c77a/beancount_import/matching_test.py) and [golden input/output directory](https://github.com/jbms/beancount-import/tree/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/testdata/matching_test/match_many_merged).

Dates are not the only evidence: `test_check_match` preserves a keyed `check: 5` match between transactions two months apart. Current single-step search tries compatible keyed metadata matches before its ordinary fuzzy date/amount window. Explicit posting dates must agree when both sides provide them; otherwise fuzzy dates are allowed. Candidate discovery's `fuzzy_match_amount` is also separate from pairwise balancing: [`get_max_residuals_from_weights`](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching.py#L847) derives permitted residuals from the two transactions' currency imbalances, requiring zero residual when either contains an unweighted posting. [Check/date tests](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching_test.py#L114), [current keyed lookup](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching.py#L387).

## 2019: fuzzy amount matching intentionally widens the candidate space

Commit [`2facf06bcd1fce6b01d224737da09470991df82f`](https://github.com/jbms/beancount-import/commit/2facf06bcd1fce6b01d224737da09470991df82f), merged through [PR #30](https://github.com/jbms/beancount-import/pull/30), changes exact-weight lookup to same-currency weights within `fuzzy_match_amount`, default 0.01. The motivating case was an exact pay-stub 401(k) deduction versus a retirement purchase whose weight is computed at greater precision. It changed indexing from `(date, amount)` to date buckets with amount filtering and similarly removed the exact amount from metadata keys. Matching/nonmatching tolerance tests and configuration plumbing accompanied the change.

This tolerance is semantic, not an accidental source of extra candidates. Its commit explicitly leaves currency-specific tolerances for future work. It does not introduce a bound on the number of equally plausible transaction partners. [Source diff and rationale](https://github.com/jbms/beancount-import/commit/2facf06bcd1fce6b01d224737da09470991df82f).

## 2020: mixed-sign groups, zero-sum protection, and large-group matching

[PR #76](https://github.com/jbms/beancount-import/pull/76) records why same-sign-only aggregation was too narrow: Amazon item prices, tax, and discounts can share one unknown expense account, and their net amount must match the credit-card expense leg.

- [`02cd249a996e04b38c039ce26181a9ac09724c44`](https://github.com/jbms/beancount-import/commit/02cd249a996e04b38c039ce26181a9ac09724c44) removed sign from aggregate grouping. This first allowed mixed-sign groups, including their full group.
- [`d1ce74d1ec8e18021cf9b670350319216783c6d4`](https://github.com/jbms/beancount-import/commit/d1ce74d1ec8e18021cf9b670350319216783c6d4) rejected aggregates summing to zero or containing a zero-sum subsubset. Its regression demonstrates retaining unrelated canceling items rather than hiding them inside a match.
- [`b5576e2f34f4446411d7994abc139b4b40bf04d4`](https://github.com/jbms/beancount-import/commit/b5576e2f34f4446411d7994abc139b4b40bf04d4) restored **per-sign** maximal groups, while keeping mixed-sign subsets only up to size four. It bypasses zero-subset checks for the large same-sign groups. Its test requires five positive items to match a payment despite an opposite-sign posting in the same account/currency group.
- [`19ff7e44b9d665ee2348bf3fdae1619d33adfab4`](https://github.com/jbms/beancount-import/commit/19ff7e44b9d665ee2348bf3fdae1619d33adfab4) avoided partitioning groups too short to need maximal-group handling. This is a small efficiency change, not a matching-policy change.

The present tests `test_match_grouped_differing_signs`, `test_match_grouped_differing_signs_sum_zero`, and `test_match_grouped_maximal_differing_signs` document the resulting distinctions. [Current test cases](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching_test.py#L832).

## 2020–2021: incomplete investment postings need special handling

[`aa79364ccd58090c97259ba84e090900dbf0a487`](https://github.com/jbms/beancount-import/commit/aa79364ccd58090c97259ba84e090900dbf0a487) guards against a missing price number. [`34051a898f946b579843b7918216927473396f8d`](https://github.com/jbms/beancount-import/commit/34051a898f946b579843b7918216927473396f8d) adds matching of unweighted postings against compatible singleton postings, including incomplete amounts, costs, and prices. It is explicitly a **partial** fix for [issue #113](https://github.com/jbms/beancount-import/issues/113), an investment-sale case; the issue remains open. The current `test_match_ofx_investment_issue113` preserves that support. [Regression test](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching_test.py#L968).

These commits matter when interpreting a “posting weight is always known” assumption: pending importer entries can legitimately be incomplete. They do not address transaction-search complexity. An extra `posting.units` crash guard existed in fork history as [`b8d3c325501caccff59b9557326bdf296342828a`](https://github.com/jbms/beancount-import/commit/b8d3c325501caccff59b9557326bdf296342828a), with a later fork variant `f9705c4`; neither guard is present in the selected upstream baseline. This is a history distinction, not a claim that #260 is caused by missing units.

## 2022–2023: indexing and aggregate limits improved throughput, with remaining ambiguity

[PR #174](https://github.com/jbms/beancount-import/pull/174), merged as [`93d7aca8bb6ce5f8d32bc2b82adf88528a33110b`](https://github.com/jbms/beancount-import/commit/93d7aca8bb6ce5f8d32bc2b82adf88528a33110b), brought several distinct optimizations:

- [`173b444f2792f0fb89fc07f2171736d881ea52fe`](https://github.com/jbms/beancount-import/commit/173b444f2792f0fb89fc07f2171736d881ea52fe) introduced date/currency buckets and batched sliding-window posting search; `are_accounts_mergeable` was cached.
- [`4514b5563cd5bf96fdebdec977b6631562374c21`](https://github.com/jbms/beancount-import/commit/4514b5563cd5bf96fdebdec977b6631562374c21) introduced `MAX_AGGREGATE_POSTINGS = 20000`. It generated all subsets first, grouped results by subset size, then stopped accepting complete sizes when the total would cross the limit. This was a bound on accepted aggregate output, not generation work or final transaction candidates.
- [`a709aba1d00c2b0ee5ce8e95e328613b8fdb78cb`](https://github.com/jbms/beancount-import/commit/a709aba1d00c2b0ee5ce8e95e328613b8fdb78cb) replaced incremental sorted insertion with append plus lazy sorting. The [review](https://github.com/jbms/beancount-import/pull/174#discussion_r962071745) identifies the previous same-bucket insertion cost as quadratic.
- [`395d4655785231283f51a8471dedfd0b3a8e2c42`](https://github.com/jbms/beancount-import/commit/395d4655785231283f51a8471dedfd0b3a8e2c42) raised the limit to **30000**, the current value, and checked it per account/currency group and subset size during the main loop. Maximal same-sign groups are appended separately. Group iteration follows input order; a size that would cross the accumulated result limit is discarded whole, and its group's larger sizes are skipped. Later account/currency groups are still considered. This differs from the original global size ordering.
- [`73ffb6efefd88110ebca6d87a6fc392110b55b4b`](https://github.com/jbms/beancount-import/commit/73ffb6efefd88110ebca6d87a6fc392110b55b4b) cached aggregate generation in an LFU cache of 1024 entries, keyed by the identities of eligible uncleared postings. The commit reports one case improving from over 7000 seconds to 240 seconds; that is a historical author benchmark, not a measurement from this investigation.

The author explicitly reported that improved lookup still produced many spurious matches because large invoice subsets matched unrelated ledger transactions. Payment-plus-tip matching was useful, while most other incidental subsets were not. [Author's account](https://github.com/jbms/beancount-import/pull/174#issuecomment-1292807291). Later reports still described hundreds of seconds for large invoices and pointed toward pairwise match-group generation as another costly area. [Performance follow-up](https://github.com/jbms/beancount-import/pull/174#issuecomment-1409092947), [next investigation targets](https://github.com/jbms/beancount-import/pull/174#issuecomment-1409513355).

The review also contains a useful failed experiment: a faster-looking bisect alternative was returning zero matches because of a bug; after correction, reported search times were 2.1 seconds for bisect versus 0.93 seconds for sliding iterators. [Author's correction](https://github.com/jbms/beancount-import/pull/174#discussion_r991642319). This is direct evidence that output equivalence matters alongside timing.

`MAX_AGGREGATE_POSTINGS` is not a universal hard ceiling: maximal same-sign groups are added outside its checks, and it neither limits pairwise correspondence enumeration nor transaction DFS states. Its current implementation also counts accepted, nonzero aggregate candidates, so a high number of rejected zero-sum subsets can still require work. These are deductions from the [current generator](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching.py#L933).

## 2023: preprocessing speedup and a correctness regression from indexing

[PR #194](https://github.com/jbms/beancount-import/pull/194), commit [`f108b59eb4a0544a325d2746b6d704958c446365`](https://github.com/jbms/beancount-import/commit/f108b59eb4a0544a325d2746b6d704958c446365), replaces truth-value checks on posting weights with explicit `is not None` checks. This prevents valid zero amounts from being treated as absent.

[PR #214](https://github.com/jbms/beancount-import/pull/214), commit [`3bcd35b1078d1a86680fea01bff7131a695d57f9`](https://github.com/jbms/beancount-import/commit/3bcd35b1078d1a86680fea01bff7131a695d57f9), reuses posting-ID keys and hoists `SearchPosting` construction outside the fuzzy-date loop. Its author reports preprocessing a 12,000-transaction ledger falling from 11.84 to 5.98 seconds. It avoids repeated work; it does not prune valid matches or change DFS.

[PR #210](https://github.com/jbms/beancount-import/pull/210), commit [`c8313234284cd891f9e65793aab2606dca325277`](https://github.com/jbms/beancount-import/commit/c8313234284cd891f9e65793aab2606dca325277), fixes a bisect lower-bound off-by-one introduced in [`8ccfee5b4ce662f8e070a90a9c0961769488391e`](https://github.com/jbms/beancount-import/commit/8ccfee5b4ce662f8e070a90a9c0961769488391e). The old slice began one element below `bisect_left`, admitting a posting outside the fuzzy amount range and provoking #202. It adds an invariant assertion, a lower-bound regression with the target at the end of the candidate list, and an upper-bound regression. The earlier negative test had the target at the beginning, where the erroneous expression happened to work. [Test-coverage explanation](https://github.com/jbms/beancount-import/pull/210#issuecomment-1817700758).

## The earlier unmerged limit proposal: PR #224

[PR #224](https://github.com/jbms/beancount-import/pull/224) remains **open and unmerged** as of this investigation, with no issue comments, review comments, or submitted reviews returned by the API. Its author reports multi-minute CPU saturation from large Amazon orders and explicitly accepts missing a valid combination in exchange for a responsive importer.

The actual two commits are [`b7e5079d69f414d0e889a2678852449c4abeaa92`](https://github.com/jbms/beancount-import/commit/b7e5079d69f414d0e889a2678852449c4abeaa92) and head [`95b2c7df126e1ce1efa3f4ec7b8dcc70faa2104e`](https://github.com/jbms/beancount-import/commit/95b2c7df126e1ce1efa3f4ec7b8dcc70faa2104e). The [complete diff](https://github.com/jbms/beancount-import/pull/224/files) does two things:

1. For an account/currency posting list with **25 or more** postings, set `max_subset_size` to 1 rather than 4. No 2–4 subsets are then generated; the per-sign maximal-group branch still runs. The commit title says “>25,” but the code uses `len(posting_list) < 25` for the ordinary path.
2. In transaction DFS, recurse only when the current `level <= 6`. Because the root is level 0 and the test precedes the child call, it permits a merged state at level 7: the root plus seven additional transactions. It still calls `get_single_step_extended_transactions` at level 7 and discards yielded children. The guard does not cap the number of alternatives at any shallower level or the work generating a single child merge.

Those are code-derived consequences, not claims from a merged fix. PR #224 contains no tests in its diff and changes matching completeness. It should not be described as an existing upstream candidate limit or as a solution already evaluated against #260.

The intervening 2024 commit [`23944c69e0fb1df1b4a259618edb085f18c7d3e1`](https://github.com/jbms/beancount-import/commit/23944c69e0fb1df1b4a259618edb085f18c7d3e1), despite its GitHub Actions title, also touches `matching.py`: it changes construction of combined removals from tuple summation to a typed tuple comprehension. That is mechanical maintenance of the same per-currency removal concatenation, not a graph-search limit.

## November 2026: merged improvements address avoidable work, preserving outputs

[PR #275](https://github.com/jbms/beancount-import/pull/275), commit [`a6351d68a0424215bd0caeb9fdac6f5ad8d16309`](https://github.com/jbms/beancount-import/commit/a6351d68a0424215bd0caeb9fdac6f5ad8d16309), finally stops generating the current aggregate subset size immediately after accepted candidates would cross `MAX_AGGREGATE_POSTINGS`. Previously a 46-posting group enumerated all `C(46,4) = 163185` four-item subsets before discarding that size. Now it stops at the crossing and still discards the whole size. This preserves accepted output. The committed test expects one maximal group, 1035 pairs, 15180 triples, and no quadruples. The PR reports aggregate generation dropping from 9.0 to 1.8 seconds on a 38,000-entry journal with identical 342,674 aggregates; these figures are author-reported. The test checks resulting contents/counts, not an explicit computation budget. [Diff and test](https://github.com/jbms/beancount-import/commit/a6351d68a0424215bd0caeb9fdac6f5ad8d16309).

[PR #276](https://github.com/jbms/beancount-import/pull/276), commit [`43f5f385221c2c98733b57a919918d81be79ccab`](https://github.com/jbms/beancount-import/commit/43f5f385221c2c98733b57a919918d81be79ccab), makes index construction lazy in two ways:

- Insert singleton postings immediately; retain transactions potentially containing aggregates in `_unexpanded`, keyed by transaction date. Build their aggregates on the first lookup within the fuzzy date window. Synthetic aggregate postings have no metadata, so their effective date is their transaction's date. Removal handles both expanded and unexpanded transactions.
- Store each posting once at its own `(date, currency)`. Construct a combined fuzzy-range list only for queried keys, and update already-built lists on later addition/removal. Amount-and-ID sorting retains the old lookup order.

The PR reports building the database dropping from 6.8 to about 0.3 seconds on a roughly 30,000-transaction ledger; 14,103 lookup-equivalence checks plus removal/re-addition of 500 transactions matched prior results. These are reported validation results, not a committed reproducible benchmark: the merged diff only changes `matching.py`. It neither budgets DFS states nor eliminates work needed for dense ambiguous dates actually queried. [Diff and validation claims](https://github.com/jbms/beancount-import/commit/43f5f385221c2c98733b57a919918d81be79ccab).

[PR #286](https://github.com/jbms/beancount-import/pull/286), commit [`7796a2ce3eaffed405c0dcb0b0d6c9265fa21cfc`](https://github.com/jbms/beancount-import/commit/7796a2ce3eaffed405c0dcb0b0d6c9265fa21cfc), fixes sorting `(date, currency)` search keys when an unbooked pending entry has an unspecified price currency, such as `50 EUR @ 1.10`, alongside a known USD currency. It sorts dates first and non-string currencies after known currencies. The regression uses synthetic unbooked pending transactions. This closes a correctness hole in the search path, not a performance budget. It also resolves an assumption already questioned in the [#174 review](https://github.com/jbms/beancount-import/pull/174#discussion_r1008194207).

## Current graph transitions, ranking, and UI cost

The [single-step extension](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching.py#L1734) obtains the current merged state's matchable postings, finds partner transactions, excludes already-used transaction IDs and incompatible metadata/opposite known postings, then computes **all** pairwise merged results. Multiple valid posting mappings can yield multiple children for one partner. It additionally tries removal of opposite unknown postings only for eligible postings that did not match normally. Existing filtering removes dominated correspondence sets **within pairwise merging**; it is not a global dominance filter over transaction subsets. [Pairwise generator and dominance filter](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching.py#L1485).

The [outer DFS](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching.py#L1839) records every new state that uses at least two transactions and then continues extending it. Its deduplication prevents revisiting the same identity/posting state through a different merge order. Since used transaction IDs are part of the key, distinct transaction subsets remain distinct even when their displayed postings look the same. Deduplication therefore removes redundant permutations without providing a polynomial bound on the number of subsets. That is the mechanism consistent with #260; no private ticket data is available to establish every detail of the reported case.

Ranking happens **after** all DFS results have been built. The [ranking key](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/matching.py#L581) is still the 2016 match-count key. Equal-rank results preserve discovery order under the stable sort; discovery order comes from posting search and partner enumeration, not an explicit quality score. Increasing the number of compatible matched postings can favor a larger merged subset even if transactions are merely similar. These are deductions from current ranking and traversal, not evidence that a particular ticket candidate is wrong.

The caller [`LoadedReconciler._make_candidates_from_import_result`](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/reconcile.py#L1077) then appends the unmerged original, predicts unknown accounts, and constructs staged candidate objects for each result. Thus reducing backend match generation would also reduce later per-result prediction/staging/encoding work, but a UI-only display limit would leave the exhaustive backend work intact. Current provenance handling additionally filters candidates that would partially consume a grouped modified journal entry. [Caller/provenance logic](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/reconcile.py#L1083).

Provenance is operational data: staging changes or removes the existing transactions used by a candidate, and accepting it consumes the corresponding pending transaction identities. Two candidates with identical rendered postings can therefore have different effects on the journal and remaining pending imports. Recent [PR #289](https://github.com/jbms/beancount-import/pull/289), commit [`da03061`](https://github.com/jbms/beancount-import/commit/da03061), specifically preserves unconsumed directives after partial matches. Removing duplicate displayed text is consequently not equivalent to deduplicating semantically identical actions. [Staging](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/reconcile.py#L1035), [acceptance](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/reconcile.py#L1155).

The server's [`Got next candidates` timing](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/webserver.py#L566) wraps the complete reconciler call, so #260's 11.3797 seconds is not an isolated DFS profile. The frontend [maps all candidates to components](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/frontend/candidates.tsx#L483); excluding a used transaction filters this already-generated list. Pending [mouse hover only updates highlighting](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/frontend/pending.tsx#L135). Selecting/skipping to an entry invokes [`handle_skip`](https://github.com/jbms/beancount-import/blob/3ee9c4045d29d47be5b1ea08a8f1b23f041db2b4/beancount_import/webserver.py#L655), which recomputes its candidates. Therefore the issue's casual description of hovering should not be turned into a claim that current hover handlers themselves call matching.

## What #260 establishes, and what remains unmeasured

[Issue #260](https://github.com/jbms/beancount-import/issues/260), opened 2026-02-07, remains open with no comments. It reports 13 similar subway purchases over several days, a visible binary-count-like progression of candidates, and roughly 11 seconds for the affected entry versus about 10 milliseconds for ordinary entries. Its title describes `2^(N-1)` candidates; its body suggests either a generation limit or limiting ranked potential partners. Those are the reporter's suggested directions, not accepted design requirements or tested fixes.

A separate synthetic cross-check performed during this research reproduces the reported growth on the selected baseline: create N identical, uncleared, same-date transactions, each with `Assets:Cash -3 USD` and `Expenses:FIXME 3 USD`, and no metadata. Searching one of them produces 7 merged candidates for N=4, 63 for N=7, 511 for N=10, and 4095 for N=13. The caller's unmerged original adds one, yielding exactly `2^(N-1)` visible candidates. The N=13 matcher run took about 10.93 seconds on this environment. All rendered merged transactions are identical; their provenance sets differ, and the first-ranked candidate consumes all N transactions. Each transaction has only one posting per account, so this example requires **no aggregate posting subsets**. These are synthetic observations, not a reconstruction of the reporter's private entries, and timing is environment-dependent.
